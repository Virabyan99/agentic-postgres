# 0050 — A reviewed API surface is a generated artifact with an update/check split

Status: accepted
Date: 2026-08-10
Session: 5, Run 1
Affects: API-CONTRACT-001, API-SCHEMA-001, API-CACHE-001

## Context

The OpenAPI document PostgREST serves cannot be committed before the locked
PostgREST has generated it, and privileged work runs from a clean immutable
installed release (ADR 0037). So the first snapshot is produced by a deployment
of a commit that does not yet contain it — a genuine ordering problem.

The runbook solves it with new machinery: a root-only
`deploy.sh --capture-session-5-contract` submode, a `session-05-capture-state.json`
document with its own schema, a deployment state that is neither ready nor
public, and a final gate that fails if any capture residue remains.

This repository has solved the same problem three times already, and always the
same way:

| Artifact | Generator | Offline check |
|---|---|---|
| `versions.env` | `bin/lock-versions.sh --update` | `--check` |
| `migrations/released.lock.json` | the migration renderer | preflight comparison |
| `docs/acceptance-matrix.md` | `bin/render-acceptance-matrix.py` | `--check`, in the gate |

Each is generated by a privileged or deliberate act, committed by a human, and
compared — never rewritten — by the gate.

## Decision

**The API surface is a fourth artifact of that shape, not a fourth mechanism.**

Two source-controlled files:

- `contracts/postgrest-api-surface.yaml` — hand-written and reviewed. Every
  exposed relation, column, RPC, argument and method named exactly. No
  wildcards, no SQL, no project-specific value.
- `contracts/postgrest-openapi.canonical.json` — **generated**. The live
  document, normalized to a project-neutral form with project-specific fields
  replaced by fixed typed sentinels.

Two commands, and the split is the point:

- `bin/api-contract.sh --update` is privileged, runs against a deployed release,
  fetches the document over the project-internal network with a short-lived
  documentation token, normalizes it, and writes a candidate. It **writes no
  source file**; the unprivileged owner reviews the diff and commits.
- `bin/api-contract.sh --check` compares. Offline it compares the committed
  snapshot against the committed surface contract. In host mode it also compares
  the live document against both. **It never writes.** The gate runs only this.

The sequence is therefore: deploy, capture, review, commit, redeploy, gate.
Session 4 already deploys twice for a structurally identical reason — an
allocation cannot be reserved before the cluster that carries its identity
exists (D112) — so "two deploys" is the established shape rather than a new one.

**No capture mode, no capture-state document, no non-ready deployment kind.**
The first deploy publishes what it always publishes; what it does not yet have
is an approved snapshot, and the gate says so by failing `--check` rather than
by inspecting a marker file.

## Consequences

**The gate cannot approve its own subject.** `--check` has no code path that
writes either contract file, and a contract test asserts that: the module
exposes no writer reachable from the check entry point. That is the property the
runbook's "the final gate uses compare-only mode and must never rewrite the
approved contract" was asking for, obtained structurally instead of by
discipline.

**An unlisted object in `api` is a release failure even when it is invisible.**
The surface contract is compared against the *catalog*, not only against
OpenAPI, because `openapi-mode = follow-privileges` hides an object whose grants
happen to exclude the documentation role — and the next grant change publishes
it.

**Two projects share one canonical snapshot.** Normalization replaces host, base
path, title suffix and server metadata with sentinels, and the per-project form
carries the real values and is published to the documentation service. The
comparator validates the real values separately *before* substituting, so a
project whose host is wrong fails rather than normalizing into agreement.

**The reload proof does not need a staged migration.** Because the snapshot is
captured from a running deployment rather than from a migration boundary, there
is no reason to stop the migration set part-way. `API-CACHE-001` is proved by
the transient acceptance object the timeout tests already require: create,
`NOTIFY`, observe the fingerprint change and the container's start time
unchanged, drop, `NOTIFY`. That path is the one every future migration uses.

**A dirty tree still cannot run privileged tooling.** `--update` runs against an
installed release like everything else privileged here; the dirty tree it
produces belongs to the unprivileged source owner, and the next deploy installs
the clean commit that follows it.

## Alternatives considered

**The runbook's capture submode.** Rejected on two counts. It is a fourth
mechanism for a problem with three existing solutions, and "this one is about an
API" is not a difference. And it invents a *deployment state* — deployed, not
ready, not public — that nothing else in the system knows how to reason about:
`deployed_through_session`, the endpoint `status` fields and the systemd
launcher would each have to learn it, and a project left in it by a failed run
is a project no other tool can describe.

**`bin/migrate.sh migrate-through --version 0007`.** Rejected with it. A second
way to apply released migrations is a second answer to "what has been applied",
inside the one plane whose immutability is a contract. D110 is the standing
lesson: inventing a route through the script whose job is to bound what may be
asked is a change made deliberately with its own test, not as a side effect of
arranging a proof.

**Commit the raw per-project document instead of a canonical form.** Rejected:
two projects would need two committed snapshots that differ only in host and
title, and the diff a reviewer reads would be dominated by the fields that carry
no meaning.

**Generate the surface contract from the catalog too.** Rejected, and this is
the one place the pattern deliberately stops. A contract generated from the
thing it constrains cannot refuse it. The surface file is hand-written because
its whole function is to disagree with the catalog when the catalog is wrong.
