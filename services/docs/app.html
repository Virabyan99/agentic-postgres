Before you read the verbs

This document is generated from the service's own route definitions, not from database privileges — so unlike the REST reference, what it advertises is what the service implements.

A client never submits a role or a scope. Both are read from server-side records, sorted and deduplicated before signing, and refused outright if the stored value is outside the committed vocabulary. A request that names one is refused rather than honoured.

The document is a reviewed snapshot, not a live capture. It is what a human approved for this release.

If you are using the object storage endpoints

An upload URL and a download URL are bearer credentials. Anyone holding one can perform the operation it authorizes, for as long as it lasts. They are returned to you once and are stored nowhere; treat them the way you would treat a password.

Deleting an object does not revoke a download URL that has already been issued. Nothing in this system can withdraw one. The exposure is bounded by expires_in and by nothing else, which is why the download lifetime is shorter than the upload's. If a URL has leaked, waiting out its expiry is the remedy — deleting the object is not.

Send an upload URL the headers the response names. The URL is signed over If-None-Match: *, so each one authorizes exactly one first write. Omitting the header does not give you an unconditional write — the provider answers 403, which looks exactly like a broken credential from where you stand. A second write to the same URL answers 412.

You cannot choose a key or a bucket, and there is no endpoint that lists your objects. The server generates the key; no request model here has a field for one. Keep the object_id you are given at upload time — it is how you complete, download and delete, and nothing will enumerate it for you.

A 404 from an object endpoint means absent, not yours, not yet complete, or already deleted. It is deliberately one answer for all four, so it is not a signal that you have found something.
